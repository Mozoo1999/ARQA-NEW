# معمارية ARQA القابلة للتوسع

## القرار المعماري

تبدأ ARQA كـ **تطبيق موحد مقسّم إلى وحدات نطاقية (Modular Monolith)**، وليس شبكة خدمات مصغرة. هذا يحافظ على سرعة البناء واتساق المعاملات في الـMVP، ويترك حدودًا واضحة لاستخراج وحدة إلى خدمة مستقلة عند الحاجة الفعلية.

## النطاقات الأساسية

```text
Platform
├─ الهوية والصلاحيات والمنظمات
├─ البيانات المرجعية: مواقع، عملات، وحدات، مراكز تكلفة
├─ CRM: عملاء، جهات اتصال، عقود
├─ Supply: موردون، مصادر، منتجات، أسعار، عروض وأوامر
├─ Fleet & Trips: مركبات، سائقون، نقلات، إثبات تسليم
├─ Projects: احتياجات، إنجاز، ميزانية، ربحية
├─ Finance Operations: فواتير، مدفوعات، ذمم ومراكز تكلفة
└─ Intelligence: مؤشرات، تنبيهات، توصيات قابلة للتفسير
```

## قواعد الحدود

1. لكل نطاق واجهة خدمة وملكية واضحة لبياناته؛ لا يكتب نطاق في جداول نطاق آخر مباشرة.
2. الكيانات المشتركة محدودة: المنظمة، المستخدم، العميل، المورد، المنتج، المشروع، الموقع، العملة والوحدة.
3. تستخدم الواجهات الداخلية أوامر وقراءات صريحة، لا تبادلًا عشوائيًا للجداول.
4. يُنشر حدث تشغيلي بعد كل تغيير مهم، مثل `quote.approved` و`trip.delivered` و`invoice.paid`.
5. لا تعتمد التقارير والذكاء الاصطناعي على الجداول الحية وحدها؛ تُبنى طبقة تحليلات/أحداث منفصلة تدريجيًا.

## مسار البيانات

```text
إدخال المستخدم أو التكامل
        ↓
وحدة النطاق + تحقق وصلاحية
        ↓
قاعدة تشغيلية + سجل تدقيق
        ↓
حدث موثوق (Outbox)
        ↓
تحليلات / تنبيهات / تكاملات / وكلاء AI
```

نمط **Outbox** يمنع فقد الحدث عندما تنجح معاملة قاعدة البيانات ولا ينجح الإرسال الخارجي.

## طبقات المنتج

| الطبقة | مسؤوليتها |
| --- | --- |
| الواجهة | لوحة عمل عربية، صلاحيات، إدخال والتحقق من السياق |
| API | حالات الاستخدام، سياسات الاعتماد، الحدود بين النطاقات |
| النطاق | قواعد الأعمال ومحرك سلسلة التكلفة |
| البيانات | PostgreSQL تشغيلي، ملفات/صور في تخزين كائنات، سجل تدقيق |
| التكامل | أحداث، Webhooks، استيراد/تصدير، مزود خرائط وGPS مستقبلًا |
| التحليلات | مستودع قياس وطبقة مؤشرات بعد نضج بيانات التشغيل |

## تصميم AI

وكلاء ARQA يقرؤون من واجهات نطاقية موثوقة وطبقة تحليلات، ولا يملكون صلاحية تعديل قاعدة البيانات مباشرة.

| الوكيل | يقرأ | يقترح | يحتاج اعتمادًا؟ |
| --- | --- | --- | --- |
| وكيل التسعير | أسعار، نقل، جودة، مشروع | مصدر وهامش وسعر بيع | نعم عند إرسال عرض |
| وكيل المشتريات | احتياجات، سعات، أسعار | أمر شراء وتوزيع كمية | نعم |
| وكيل النقل | رحلات وسائقون وسعات | خطة نقل وتنبيه تأخير | نعم قبل تعديل خطة |
| وكيل المدير | مؤشرات ومخاطر | أولوية أو تنبيه | لا يغيّر تشغيليًا |

كل اقتراح يحفظ مصدر البيانات ووقت التوليد والبدائل والسبب وموافقة أو رفض المستخدم.

## تصميم IoT

بوابة إدخال منفصلة تستقبل القياسات الخام من GPS، الوقود، الأوزان والكاميرات. تربط القياس برحلة أو مركبة أو أصل بعد التحقق، ولا تكتب مباشرة في سجلات الأعمال النهائية.

- القياسات الخام غير قابلة للتعديل وتحمل وقت الجهاز ووقت الاستلام.
- معرّف الجهاز وسرّ الاتصال منفصلان عن بيانات العامل والمركبة.
- الصور والتوقيعات تحفظ كملفات مع روابط وسجل وصول.
- تدفق القياسات الكبير لا يضغط قاعدة بيانات العمليات.

## أمن وخصوصية

- صلاحيات مبنية على المنظمة والدور والمشروع، لا على الشاشة فقط.
- سجلات تدقيق لا تُحذف للموافقات والأسعار والرحلات والتكاليف.
- تشفير أسرار أجهزة IoT ومفاتيح التكامل.
- بيانات السوار والصحة منفصلة وحساسة؛ لا تدخل الـMVP ولا تُجمع دون سياسة قانونية وموافقة صريحة.
